# 长文本翻译

本技能提供三条翻译路径，根据文本规模和用户需求自动判断或由用户指定：

1. **普通翻译**：主 agent 在单一上下文中一次性完成翻译，仅输出最终译文。适合短文本和论证紧密、不宜分片的文章。
2. **长文本翻译**：先分片，主 agent 建立共享中间文件后委派 subagent 并行翻译各分片，最后合并与自检。产物包含最终译文及全部中间文件。
3. **译稿审校与润色**：对已有译文进行审校和润色。既可作为前两种路径完成后的增强流程，也可在用户直接提供原文与译文时独立执行。

## 前置准备

### 第 1 步：规范化源内容

翻译流程只接受 Markdown 输入。若用户提供的是 PDF 或 EPUB 文件，先按对应 ingestion 指南将其转换为本地 Markdown；若用户只要求翻译源材料的一部分（如指定章节、页码或标题范围），则先抽取并保存该范围内容。

**规范化后的 Markdown 文件，是后续所有翻译步骤的唯一输入源。**

| 输入类型 | 动作 |
|------------|--------|
| 文本 / Markdown 文件 | 直接使用 |
| 内联文本 | 保存为 `translate/{slug}.md` |
| PDF 文件 | 按 `references/ingest/pdf.md` 处理并保存为 `translate/{slug}.md` |
| EPUB 文件 | 按 `references/ingest/epub.md` 处理并保存为 `translate/{slug}.md` |
| 只翻译源文本的部分内容 | 抽取指定范围，保存为 `translate/{filename}-part.md` |

`{slug}`：根据内容主题生成的 2–4 个词、采用 `kebab-case` 的短名称。

### 第 2 步：制定并确认翻译方案

**① 整理翻译偏好**

- **目标语言**：默认简体中文，用户可自行指定。
- **目标读者**：默认为希望准确、无障碍理解原文内容的读者，用户可自行指定。
- **用户术语资源**：用户显式提供的术语约束，例如术语表文件、命令中直接写出的术语映射、保留原文或指定译法等要求。非必须项；若有则完整收集并全程应用。

**② 决定翻译策略**

先对源材料做轻量分析（字数、类型、内容），再按下述顺序判断：

1. 用户已明确指定策略 → 直接按其要求执行。若用户要求中带有”精翻””精校””审校””润色””发版级质量””出版级”等关键词，必须在所选翻译路径完成后继续执行审校与润色流程。
2. 依据翻译规模判断：
   - 读取 `references/metadata.json`。若能识别当前模型且匹配到对应条目，使用该条目的 `safeBelow` 与 `chunkAbove` 阈值；否则使用文件顶层的 `fallback`。
   - 估算待译文本词数。低于 `safeBelow` 直接采用普通翻译。高于 `chunkAbove` 直接采用长文本翻译。若介于两者之间，继续评估分片风险。
3. 评估分片风险：当原文论证链紧、概念与指代跨段延续时，分片容易导致理解断档，因此仍采用普通翻译模式，并在完成摘要中建议审校与润色；否则采用长文本翻译。

**③ 准备输出目录**

明确策略后，在源文件同级目录下创建输出目录，路径格式为 `{source-dir}/{source-basename}-{target-lang}/`。

示例：
- `posts/article.md` → `posts/article-zh/`
- `translate/ai-future.md` → `translate/ai-future-zh/`

注：若目标目录已存在且是本任务的延续（如对已有译稿执行审校润色），则直接沿用原有目录及其中间文件。若已存在但不是本任务的延续，则路径改为 `{source-dir}/{source-basename}-{target-lang}-MMDD-HHMM/`（其中 `MMDD-HHMM` 代表当前日期和时间）。

**④ 生成分片预览（仅限长文本翻译模式）**

如采用长文本翻译模式，需先生成分片预览。请执行以下命令：

`python3 {baseDir}/scripts/chunk.py preview <file> [--max-words <chunk_max_words>] --output-dir <output-dir>`

其中，`{baseDir}` 为本 SKILL.md 所在目录，`<chunk_max_words>` 即前述的 `safeBelow`。

此命令将生成 `{output-dir}/chunk-preview.html`，并自动启动本地预览服务（15 分钟无操作后自动关闭），但不会立即创建 `chunks/` 文件夹。用户可通过命令返回的 `preview_url` 访问分片预览页面，在线调整分片并点击“确认分片方案”后，分片配置将保存为 `{output-dir}/chunk-plan.json`（该确认操作通过本地 server 执行，直接打开 html 文件无效）。后续实际分片时，脚本会优先读取此文件，如不存在则采用默认分片方案。

**⑤ 声明翻译计划并等待确认**

初步确定翻译方式和输出目录后，告知用户，并征求确认。参考模板：

```
{translation_strategy}。{strategy_explanation}。

翻译方案：

- 目标语言：{target_language}
- 目标读者：{target_audience}
- 术语约束：{glossary_resources}
- 输出目录拟定为：{output-dir}
- {chunk_preview}

如果你确认，我就开始翻译；如果你想调整语气、读者或术语，直接告诉我。
```

- `{translation_strategy}` 填入具体路径名称，如“普通翻译”“长文本并行翻译”“普通翻译 + 审校润色”“已有译稿审校润色”等。
- `{strategy_explanation}` 用一句话说明判断依据，与策略名称自然衔接为一个完整句子。
- `{chunk_preview}` 仅在采用长文本翻译模式时出现，内容为：“分片预览：{preview_url} —— 可在线调整分片边界，点击“确认分片方案”即生效；无需调整可跳过。”

### 第 3 步：准备执行材料

**输出目录文件清单**：

| 文件 | 出现场景 | 说明 |
|------|----------|------|
| `translation.md` | 所有模式 | 最终译文 |
| `chunk-preview.html` | 长文本 | 本地预览服务使用的页面文件；用户应通过 `preview_url` 打开 |
| `chunk-plan.json` | 长文本 | 用户在预览页面确认后的分片方案；若未生成则按默认分片执行 |
| `glossary.md` | 长文本 | 术语约束 |
| `prompt.md` | 长文本 | 共享翻译提示 |
| `chunks/` | 长文本 | 源分块与已翻译分块 |
| `goal.md` | 审校润色 | 翻译目标 |
| `draft.md` | 审校润色 | 审校前译稿快照 |
| `critique.md` | 审校润色 | 结构化、可证伪的独立审校报告 |
| `revision.md` | 审校润色 | 基于审校意见修订后的译文 |

**长文本分片（仅限长文本翻译模式）**：

用户确认翻译方案后，运行 `python3 {baseDir}/scripts/chunk.py materialize <file> [--max-words <chunk_max_words>] --output-dir <output-dir>` 将分片方案落地为 `chunks/` 下的分块文件。

注：脚本依赖 `markdown-it-py>=4.0,<5`。

## 翻译执行

### 第 1 步：理解内容并确定译法

本步骤承接前置准备中确定的翻译策略、目标读者和术语约束，深入分析源材料并做出译法判断。翻译原则保持通用，具体取舍由本步骤的译法判断决定。

**① 内容理解**

核心论点是什么？作者背景、立场和写作语境？原文的目的和预期受众？

**② 术语**

识别需要全局统一的术语，与前置准备中收集的用户术语资源交叉核对；对术语表中未覆盖的术语，确定标准译法。

**③ 译法判断**

- **语域锚定**：原文的正式度/口语度处于什么位置？基于目标读者，译文应锚定在何种语域？→ 驱动"语气与语域匹配"原则。
- **格式增强许可**：原文有无固有章节/标题结构？论证形式是松散散文还是严密论证？中文读者是否需要额外的格式导航（加粗关键句、插入小标题）？→ 驱动"格式增强"是否启用。
- **注释策略**：基于目标读者，哪些术语和背景概念需要解释？密度如何？→ 驱动"译者注"的执行策略。
- **句式策略**：原文句长和复杂度特征？中文拆句到什么程度？→ 驱动"重写"原则的执行力度。

**④ 翻译难点**

不能直译的隐喻、习语、表达；长难句、双关、文字游戏等需要创造性处理的结构。

在普通翻译模式下，本步骤仅作为内部推理参考，无需生成文件或向用户输出分析内容。

### 第 2 步：翻译

开始翻译前，回顾第 1 步「译法判断」的四项决定（语域锚定、格式增强许可、注释策略、句式策略），在翻译过程中贯彻执行。

**必须遵守的原则**：

- **准确第一**：忠实原文，完整保留原文事实、数据、观点、逻辑关系和论证结构。
- **重写，而不只是翻译**：不改变原意的前提下，将内容重写为自然流畅的目标语言，如同母语作者从零创作。为此需做到：（1）不受原文句子边界的约束——将英文长句拆成中文惯用的短句，或将原文松散的短句整合为流畅的段落节奏；（2）不跟随原文的从句嵌套顺序——按中文的自然信息排列习惯重组；（3）同一句话的中文表达是否成立，只取决于"中文母语作者会不会这样写"，而非"是否对应了原文的每个词"。具体拆句力度由「译法判断」中的句式策略决定。
- **语气与语域匹配**：原文的口语化程度、情感强度、讽刺或幽默，译文必须等价再现，不得遁入中性书面语；原文是严谨论述，译文同样必须保持正式语域和精确性。匹配是双向的，具体锚定点由「译法判断」中的语域锚定决定。不要因为翻译过程的逐字对照而自动削弱语调。
- **保留与增强 Markdown 格式**：标题层级、链接、图片、代码块等结构性标记须原样保留。增强操作（为关键论断句加 **粗体**、为缺少导航节点的长文插入小标题）是否启用，由「译法判断」中的格式增强许可决定。斜体、脚注等语义格式在中文中优先转换为合适的等价格式（如用引号或书名号替代斜体）。注意保留原文中独立于引用块之外的叙述性插入（如 `*(long pause)*`、`*[场景描述]*`）的段落归属——它们不是对话的一部分，不应被收编进 blockquote。
- **术语标准**：严格遵守用户提供的术语约束（但不能替代语境判断，应具体分析）。若无术语约束，专业术语使用行业公认的标准译法。核心术语首次出现时，在译文后用括号标注英文原文。
- **严禁静默纠错**：若原文存在拼写错误、明显 OCR 错字等低争议错误，可在译文中直接修正，但译后必须向用户汇报。

**译者注**：注释策略（是否添加、添加密度）由「译法判断」中的注释策略决定。如需添加，格式为粗体括号 `（**解释**）`。

### 第 3 步：译后自检

回源抽查译文，检查以下质量门禁：

- **准确性**：事实、数据、观点、逻辑关系和论证结构、作者立场无偏移
- **完整性**：无漏译、无增译、无跳段、无重复
- **语气**：情感强度和语域是否匹配原文（口语/讽刺/幽默是否被中性书面语抹平）
- **术语**：用户指定术语是否正确应用、会话确认术语是否一致、专业术语首次出现是否标注原文
- **格式**：对照「译法判断」中的格式增强许可——若决定启用，是否已为关键论断句加了粗体、是否已为长文插入小标题。Markdown 结构性标记（标题、链接、图片、代码块）是否完整。叙述性插入（如场景指示）是否保持在引用块内外与原文一致的位置
- **可读性**：无病句、无明显翻译腔、指代清楚、信息密度和句长符合目标语言阅读习惯

局部问题应直接就地修正。若发现跨段落、跨章节的系统性问题（如术语漂移、语气风格不一致或叙述口径摇摆），应先在当前译文中尽可能修正明显问题；若仍判断需要全局审校，则在完成摘要中明确说明问题类型、可能影响，并建议用户启动审校润色流程。

### 第 4 步：完成摘要

若需要继续执行审校与润色流程，在完成该流程后再汇报完成摘要。

```
翻译完成，译文已保存至 {output-dir}/translation.md。是否需要进一步审校与润色？
```

如有需要向用户反馈的争议或疑问，请补充：

```
本次翻译发现以下争议或不确定之处：
1. …
2. …
```

### 长文本翻译模式

同样需先完成第 1 步「理解内容并确定译法」，但若源文件过大导致读取 token 受限，则先建立整体认识（书名与作者、大致章节数、目录结构、核心主题与学科领域）即可，译法判断聚焦可判断的维度。

翻译原则不变，但执行流程替换为：

1. **提取术语**：扫描整篇文档，找出专有名词、技术术语、重复短语。
2. **建立会话术语表**：将提取出的术语与用户术语约束合并，确定一致译法，整理为 `glossary.md`。
3. **组装翻译提示**：将第 1 步的产出——内容理解、术语、译法判断、翻译难点——按 `references/prompt-template.md` 第 1 部分组装为共享上下文，保存为 `prompt.md`（仅共享上下文，不含任务指令）。译法判断中的语域锚定、注释策略和句式策略是 subagent 保持一致性的关键输入。
4. **委派 subagent 起草**：为每个分块启动一个 subagent，按可承受的并发能力分批执行（模板第 2 部分）。每个 subagent 读取 `prompt.md` 获取共享上下文，接收分块位置信息（第 N 块，共 M 块 + 该块在论证中所处位置的简要上下文），翻译自己的分块并保存到 `chunks/chunk-NN-draft.md`。一致性由共享的 `prompt.md` 保证。
5. **合并**：所有 subagent 完成后，按顺序合并已翻译分块。若存在 `chunks/frontmatter.md` 则置于开头。保存为 `translation.md`。所有源分块与已翻译分块均保留在 `chunks/` 中。

译后自检由主 agent 对合并后的初稿进行。除前述质量门禁外，还需额外检查：论证接续、指代清晰度、语气一致性、术语一致性，以及是否存在重复或漏译。处理方式同上：局部问题就地修正，系统性问题在修正基础上通过完成摘要建议审校润色。

最后，输出完成摘要。

## 译稿审校与润色

审校与润色是增强流程，用于降低误译风险，并使译文作为自然的目标语言文章成立。本流程非默认执行，仅当满足以下任一条件时触发：

- 用户明确要求精翻、审校、润色或发布级质量
- 待译文本词数处于 `safeBelow` 与 `chunkAbove` 区间，但仍采取普通翻译模式
- 主 agent 在译后自检中发现无法局部修正的系统性问题

执行总则：先诊断，后修订，再润色。具体流程覆盖两种情况：

1. **已有完整翻译过程**：译文由本技能前述流程逐步生成，上下文与中间文件完整。
2. **直接提供原文与初稿**：用户直接提交源材料与译文初稿，未经过翻译流程。

详细执行细节阅读：`references/polish.md`。
