# 长文本翻译

本技能提供三条翻译路径，根据文本规模和用户需求自动判断或由用户指定：

1. **普通翻译**：主 agent 在单一上下文中一次性完成翻译，仅输出最终译文。适合短文本和论证紧密、不宜分片的文章。
2. **长文本翻译**：先分片，主 agent 建立共享中间文件后委派 subagent 并行翻译各分片，最后合并与自检。产物包含最终译文及全部中间文件。
3. **译稿审校与润色**：对已有译文进行审校和润色。既可作为前两种路径完成后的增强流程，也可在用户直接提供原文与译文时独立执行。

## 前置准备

### 第 1 步：规范化源内容

翻译流程只接受 Markdown 输入。若用户提供的是 PDF 或 EPUB 文件，先按对应 ingestion 指南将其转换为本地 Markdown；若用户只要求翻译源材料的一部分（如指定章节、页码或标题范围），则先抽取并保存该范围内容。

**规范化后的 Markdown 文件，是后续所有翻译步骤的唯一输入源。**

| 输入类型 | 动作 |
|------------|--------|
| 文本 / Markdown 文件 | 直接使用 |
| 内联文本 | 保存为 `translate/{slug}.md` |
| PDF 文件 | 按 `references/ingest/pdf.md` 处理并保存为 `translate/{slug}.md` |
| EPUB 文件 | 按 `references/ingest/epub.md` 处理并保存为 `translate/{slug}.md` |
| 只翻译源文本的部分内容 | 抽取指定范围，保存为 `translate/{filename}-part.md` |

`{slug}`：根据内容主题生成的 2–4 个词、采用 `kebab-case` 的短名称。

### 第 2 步：制定并确认翻译方案

**(1) 整理翻译偏好**

- **目标语言**：默认简体中文，用户可自行指定。
- **目标读者**：默认为希望准确、无障碍理解原文内容的读者，用户可自行指定。
- **用户术语资源**：用户显式提供的术语约束，例如术语表文件、命令中直接写出的术语映射、保留原文或指定译法等要求。非必须项；若有则完整收集并全程应用。

**(2) 决定翻译策略**

先对源材料做轻量分析（字数、类型、内容），再按下述顺序判断：

1. 用户已明确指定策略 → 直接按其要求执行。若用户要求中带有「精翻」「精校」「发版级质量」等关键词，在所选翻译路径完成后自动衔接审校与润色。
2. 依据翻译规模判断：
   - 读取 `references/metadata.json`。若能识别当前模型且匹配到对应条目，使用该条目的 `safeBelow` 与 `chunkAbove` 阈值；否则使用文件顶层的 `fallback`。
   - 估算待译文本词数。低于 `safeBelow` → 默认采用普通翻译。高于 `chunkAbove` → 默认采用长文本翻译。介于两者之间 → 按下一条评估。
3. 评估分片风险：当原文论证链紧、概念与指代跨段延续时，分片容易造成理解断档，优先采用普通翻译并在译后自动进入审校与润色；其他情况则采用长文本翻译。

**(3) 准备输出目录**

明确策略后，在源文件同级目录下创建输出目录，路径格式为 `{source-dir}/{source-basename}-{target-lang}/`。

示例：
- `posts/article.md` → `posts/article-zh/`
- `translate/ai-future.md` → `translate/ai-future-zh/`

注：若目标目录已存在且是本任务的延续（如对已有译稿执行审校润色），则直接沿用原有目录及其中间文件。若已存在但不是本任务的延续，则路径改为 `{source-dir}/{source-basename}-{target-lang}-MMDD-HHMM/`。

**(4) 生成分片预览（仅限长文本翻译模式）**

若策略为长文本翻译模式，需先生成分片预览供用户确认：运行 `python3 {baseDir}/scripts/chunk.py preview <file> [--max-words <chunk_max_words>] --output-dir <output-dir>`，生成 `{output-dir}/chunk-preview.html`。该命令只生成预览，不生成最终 `chunks/`。（`{baseDir}` = 此 SKILL.md 所在目录路径。）

**(5) 声明翻译计划并等待确认**

得到初步判断和路径准备后，向用户声明并等待确认。参考格式：

```
根据您的需求和源材料分析，我初步拟定了翻译方案：

- 目标语言：{{TARGET_LANGUAGE}}
- 目标读者：{{TARGET_AUDIENCE}}
- 术语约束：{{GLOSSARY_RESOURCES}}

综合文本规模、论证紧密程度等因素，建议采用 {{TRANSLATION_STRATEGY}}。
理由：{{STRATEGY_EXPLANATION}}
{{CHUNK_PREVIEW_LINE}}

请确认上述方案是否符合预期，如需调整请随时告诉我。确认后我将立即开始执行。
```

- `{{TRANSLATION_STRATEGY}}` 填入具体路径名称，如"普通翻译""长文本并行翻译""普通翻译 + 审校润色""已有译稿审校润色"等。
- `{{STRATEGY_EXPLANATION}}` 用一句话说明判断依据。
- `{{CHUNK_PREVIEW_LINE}}` 仅在采用长文本翻译模式时出现，内容为："- 分片预览：我已生成 `{output-dir}/chunk-preview.html`。如果想检查或调整分片边界，可以打开它；不调整则无视即可；如已调整，请点击页面中的'复制调整方案'并粘贴给我。"

### 第 3 步：准备执行材料

**输出目录文件清单总览**：

| 文件 | 出现场景 | 说明 |
|------|----------|------|
| `translation.md` | 所有模式 | 最终译文 |
| `chunk-preview.html` | 长文本 | 可选分片边界预览与调整界面 |
| `glossary.md` | 长文本 | 术语约束 |
| `prompt.md` | 长文本 | 共享翻译提示 |
| `chunks/` | 长文本 | 源分块与已翻译分块 |
| `goal.md` | 审校润色 | 翻译目标 |
| `draft.md` | 审校润色 | 审校前初稿 |
| `critique.md` | 审校润色 | 批判性审校发现 |
| `revision.md` | 审校润色 | 基于审校意见修订后的译文 |

**长文本分片（仅限长文本翻译模式）**：

此步将基于用户的确认反馈，将预览阶段的分片方案真正落地为 `chunks/` 目录：

- 用户未提供调整方案：直接运行 `python3 {baseDir}/scripts/chunk.py materialize <file> [--max-words <chunk_max_words>] --output-dir <output-dir>`，按默认方案生成分块文件。
- 用户提供了调整方案（从 HTML 复制的 JSON）：将该 JSON 写入临时文件，运行 `python3 {baseDir}/scripts/chunk.py materialize <file> --output-dir <output-dir> --plan-file <adjusted-plan.json>` 按调整后的方案生成分块。

注：脚本依赖 `markdown-it-py>=4.0,<5`。

## 翻译执行

### 第 1 步：理解内容

分析源材料，建立全局理解：

- **内容**：核心论点是什么？作者背景、立场和写作语境？原文的目的和预期受众？
- **术语**：识别需要全局统一的术语，与用户术语资源交叉核对；对术语表中未覆盖的术语，确定标准译法。
- **语气与风格**：正式还是口语化？是否有幽默、隐喻、文化引用？针对目标受众，译文适合何种语体？
- **翻译难点**：不能直译的隐喻、习语、表达；长难句、双关、文字游戏等需要创造性处理的结构。

在普通翻译模式下，本步骤仅作为内部推理参考，无需生成文件或向用户输出分析内容。

### 第 2 步：翻译

**必须遵守的原则**：

- **准确第一**：忠实原文，完整保留原文事实、数据、观点、逻辑关系和论证结构。
- **重写，而不只是翻译**：不改变原意的前提下，将内容重写为自然流畅的目标语言，如同母语作者从零创作。
- **保留格式**：原样保留标题、粗体、斜体、脚注、图片、公式等 Markdown 格式。
- **术语标准**：严格遵守用户提供的术语约束（但不能替代语境判断，应具体分析）。若无术语约束，专业术语使用行业公认的标准译法。核心术语首次出现时，在译文后用括号标注英文原文。
- **严禁静默纠错**：若原文存在拼写错误、明显 OCR 错字等低争议错误，可在译文中直接修正，但译后必须向用户汇报。

**非强制性要求**：可根据目标读者和源材料的具体情况，灵活决定是否为读者可能不了解的专业术语或背景概念添加简明、节制的解释，格式为粗体括号 `（**解释**）`。例如，学术文献面向大众读者时应适当补充解释；面向领域专家时则无需增添。

### 第 3 步：译后自检

回源抽查译文，检查以下质量门禁：

- **准确性**：事实、数据、观点、逻辑关系和论证结构、作者立场无偏移
- **完整性**：无漏译、无增译、无跳段、无重复
- **术语**：用户指定术语是否正确应用、会话确认术语是否一致、专业术语首次出现是否标注原文
- **格式**：Markdown 结构、链接、图片引用、代码块是否完整
- **可读性**：无病句、无明显翻译腔、指代清楚

局部问题应直接就地修正。若发现跨段落、跨章节的系统性问题（如术语漂移、语气风格不一致或叙述口径摇摆），应先在当前译文中尽可能修正明显问题；若仍判断需要全局审校，则在完成摘要中明确说明问题类型、可能影响，并建议用户启动审校润色流程。

### 第 4 步：完成摘要

```
**翻译完成**

源文件：{source-path}
语言：{from} → {to}
输出目录：{output-dir}/
最终译文：{output-dir}/translation.md
已应用术语数：{count}

是否需要进一步审校与润色译稿？
```

若有争议内容需汇报，可追加：

```
本次翻译过程中发现以下争议或模糊之处：
1. ……
2. ……
```

若发现无法局部修复的系统性问题，可追加：

```
本译稿存在以下难以局部修正的系统性问题，建议进行完整审校和润色：
1. ……
2. ……
```

### 长文本翻译模式

同样需先"理解内容"，但若源文件过大导致读取 token 受限，则先建立整体认识（书名与作者、大致章节数、目录结构、核心主题与学科领域）即可。

翻译原则不变，但执行流程替换为：

1. **提取术语**：扫描整篇文档，找出专有名词、技术术语、重复短语。
2. **建立会话术语表**：将提取出的术语与用户术语约束合并，确定一致译法，整理为 `glossary.md`。
3. **组装翻译提示**：按 `references/prompt-template.md` 第 1 部分组装共享上下文——内联"理解内容"时的判断（目标风格、内容背景、合并术语表和翻译难点），保存为 `prompt.md`（仅共享上下文，不含任务指令）。
4. **委派 subagent 起草**：为每个分块启动一个 subagent，按可承受的并发能力分批执行（模板第 2 部分）。每个 subagent 读取 `prompt.md` 获取共享上下文，接收分块位置信息（第 N 块，共 M 块 + 该块在论证中所处位置的简要上下文），翻译自己的分块并保存到 `chunks/chunk-NN-draft.md`。一致性由共享的 `prompt.md` 保证。
5. **合并**：所有 subagent 完成后，按顺序合并已翻译分块。若存在 `chunks/frontmatter.md` 则置于开头。保存为 `translation.md`。所有源分块与已翻译分块均保留在 `chunks/` 中。

译后自检由主 agent 对合并后的初稿进行。除前述质量门禁外，还需额外检查：论证接续、指代清晰度、语气一致性、术语一致性，以及是否存在重复或漏译。处理方式同上：局部问题就地修正，系统性问题在修正基础上通过完成摘要建议审校润色。

最后，输出完成摘要。

## 译稿审校与润色

本流程分为两种情况：

1. 当前译稿是从源材料经由上述翻译过程逐步生成的，上下文完整保留，可直接在此基础上审校润色。
2. 用户直接提供源材料与译文初稿，要求审校润色，无上述翻译过程。

两种情况的流程略有区别。详细执行流程见 `references/polish.md`。
